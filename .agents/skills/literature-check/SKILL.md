# Literature check

Read the [project rules](../../../AGENTS.md), [source guide](../../../references/README.md), and the [paper-note template](../../../references/paper-note-template.md). Keep the [fixed scope](../../../docs/research-plan.md) in view; checking a paper is not permission to choose a new topic.

1. Identify the source and the exact claim being checked. Use the DOI, publisher page, or preprint identifier. Confirm the title, authors, year, and version before relying on it.
2. Read the passage that supports the claim. Record its page, section, table, or figure. A search snippet or another model's summary is not that passage. If only the abstract is available, label the limit and avoid detailed claims it cannot support.
3. Record the tested PDE, parameter workload, baseline reuse, accuracy rule, hardware, and cost measure where relevant. Keep runtime and energy findings separate. Do not generalize a single-solve result to the full parameter family.
4. Write a short source note with the actual access date and the material read. Separate the paper's result from our interpretation. Record missing access, conflicts, or an identifier mismatch plainly.
5. Check the adjacent report claim against the note and narrow it to what the evidence supports. Use the [writing skill](../research-writing/SKILL.md) for the final prose.

Use browsing and download tools allowed by the host. Do not send private drafts, datasets, or credentials to a source service. Keep each download in its own new empty directory under the ignored `downloads/` path, record its source and hash, and keep executable scripts elsewhere. Do not execute a paper's downloaded code as part of a literature check.

If browsing is unavailable, do not invent verification. Return the supplied citation with an unchecked status and the next check needed. Do not rewrite submitted proposal files to repair a later-discovered citation problem. Record a correction in the active note and discuss its effect on the research.
